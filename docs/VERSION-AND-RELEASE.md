# 버전·릴리스 관리

## 버전 형식

`MAJOR.MINOR.PATCH`를 사용합니다.

- MAJOR: 설정/자산 호환성이 깨지는 큰 변경
- MINOR: 새 기능·새 행동·새 모습
- PATCH: 버그·문구·작은 프레임 수정

예:

```text
1.5.0 → 1.5.1: 위치 저장 버그 수정
1.5.1 → 1.6.0: 잠자기 동작 추가
1.6.0 → 2.0.0: 설정 형식과 애니메이션 구조 전면 변경
```

## 릴리스 순서

1. 작업 브랜치 또는 백업 생성
2. 코드·프레임 수정
3. `bump_version.py`
4. `CHANGELOG.md` 작성
5. `build_all.py`
6. Windows 실제 실행 테스트
7. macOS Intel 또는 Apple Silicon 실제 실행 테스트
8. 필요하면 코드서명·공증
9. 서명된 최종 파일을 다시 검증
10. SHA-256 기록 후 배포

GitHub에서는 `v1.5.0` 형식의 태그가 `config/project.json`의 전체 버전과
일치해야 합니다. 태그 push는 미서명 빌드가 첨부된 초안 Release를 만들며,
실기기 테스트와 서명 후 사람이 공개합니다. 자세한 순서는 `GITHUB.md`를
확인하세요.

## 필수 수동 스모크 테스트

Windows:

- 처음 실행과 중복 실행 차단
- 성견↔퍼피 전환
- 자동·조용히·앉기
- 네 수동 행동
- 드래그·더블클릭·우클릭
- 숨기기 후 트레이에서 보이기
- 클릭 통과 후 트레이에서 해제
- 세 크기
- 자동 실행 켜기·끄기
- Explorer 재시작 후 트레이 복구
- 모니터 연결 변경 후 화면 안 복귀
- 설정 제거 후 재실행 기본값

macOS:

- Control-클릭 첫 실행
- 메뉴 막대 아이콘
- 성견↔퍼피
- 자동·조용히·앉기
- 드래그·더블클릭·우클릭
- 숨기기와 클릭 통과 복구
- 세 크기와 항상 위
- 로그인 자동 실행 등록·해제
- 앱 재시작 후 설정 유지
- 설정 제거 후 기본값

## 서명 순서

서명은 빌드 마지막에 수행합니다. 서명 후 파일 바이트와 SHA-256이 바뀌므로
서명 전 해시를 최종 배포 해시로 기록하면 안 됩니다.

macOS는 `.app` 전체에 서명한 뒤 공증하고 staple한 후 ZIP을 새로 만듭니다.

## 자동 검사와 실제 실행 검사의 차이

`validate_release.py`가 확인하는 것:

- 파일 형식과 아키텍처
- 리소스/프레임 수
- 버전 일치
- ZIP CRC와 Mac 실행 권한
- 의도치 않은 셸 실행 문자열

확인하지 못하는 것:

- 실제 OS의 애니메이션 부드러움
- 트레이/메뉴 막대 UI 배치
- 백신·Smart App Control·Gatekeeper 정책
- 모든 모니터/DPI 조합
- 로그인 자동 실행의 OS 승인 흐름

따라서 자동 검사 통과는 실제 기기 스모크 테스트를 대체하지 않습니다.
